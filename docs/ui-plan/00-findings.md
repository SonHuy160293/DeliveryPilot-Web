## 2. Product purpose

DeliveryPilot is a multi-tenant B2B **Software Delivery Lifecycle Management Platform** for software outsourcing agencies (initial ICP: 10–100 staff, fixed-price client work). North star: _every delivery commitment is understandable, traceable, measurable and proactively manageable_. The MVP journey is: vendor creates a workspace → records a **client engagement** (fixed-price agreement) → creates a **Scrum project** under it → invites the **client PO as a guest** → shares selected items through the **Client Portal** → later: backlog, requirements, sign-off, Sprints, risks (not yet specified).

## 3. User roles (authorization is never a job title)

| Client decision      | **Client Product Owner** assignment on a project (exactly one admitted guest).                                                                                                                                                                                                                                                      | FR-DP-004-009                                  |

## 5. Key workflows

1. **Access** (FEAT-DP-002): register (DisplayName/Email/Password, no auto-login, duplicate message "This email is exist") → sign in → memory-only session → sign out.
2. **Workspace** (FEAT-DP-003): create workspace (become Owner) → invite with roles → recipient previews/accepts/declines with matching email → manage members, roles, ownership nominations, audit.
3. **Engagement** (FEAT-DP-025): create → set contract value/effort → add milestones → designate contacts/client PO → (optional) issue link code → client Owner/Admin confirms link → close/reopen.
4. **Project initialization** (FEAT-DP-004): create Draft project (client or internal) → brief + Product Goal → Sprint length → add member participants → invite guest → guest accepts → assign client PO → activate (gap list or waiver).
5. **Client Portal** (FEAT-DP-015): PM shares brief items / stakeholder entries / engagement summary → guest opens portal → sees default view + shared items → PM withdraws → item disappears.

## 7. Assumptions (each is also tagged inline where used)

| ID  | Assumption                                                                                                                                                                                                                               |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | New workspace-scoped pages live under `/w/:workspaceSlug/...` because the slug segment is already the validated organization UUID.                                                                                                       |
| A2  | Project sub-areas use a `?tab=` search parameter, mirroring the approved `?section=` pattern of `src/lib/workspaceSections.ts`, to minimise new routes.                                                                                  |
| A3  | Guest invitation acceptance mirrors `/join-workspace`: link carries the proof in a URL fragment; route `/join-project`.                                                                                                                  |
| A4  | Client-link confirmation (client side) is a new workspace section `?section=client-links` on `/w/:workspaceSlug`, visible to that workspace's Owner/Admin.                                                                               |
| A5  | Orphaned-project recovery is a new workspace section `?section=projects-recovery`, visible to Owners only.                                                                                                                               |
| A6  | Mock repositories simulate latency of 400 ms and support a deterministic failure switch for tests only (never via URL in production builds).                                                                                             |
| A7  | The UI can know the caller's workspace permission codes from current role badges + roles catalog (existing pattern); the server still decides. Buttons are shown optimistically only when the code is held, and every denial is handled. |
| A8  | Engagement summary visible to linked-project participants is reached from the Project overview, not from the Engagement list.                                                                                                            |
